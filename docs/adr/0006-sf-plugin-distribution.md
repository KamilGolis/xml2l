# xml2l ships as a Salesforce CLI plugin

`xml2l` is distributed as a Salesforce CLI plugin, `sf-plugin-xml2l`. Installing it with `sf plugins install` provides `sf xml2l profile diff|save|convert` and `sf xml2l permset convert`. The plugin mirrors the binary's commands and flags one-for-one and adds no behaviour of its own: sf supplies help, flag validation, `--flags-dir` and the JSON envelope, while the binary keeps owning normalization and the machine document.

The executable arrives through platform npm packages — `xml2l-<os>-<arch>` for darwin, linux and win32 on x64 and arm64 — declared as optional dependencies of the plugin. npm's resolver installs exactly the matching package, so no install script runs and `--ignore-scripts`, proxies and registry mirrors do not break the install. The alternatives lost on evidence rather than taste. A tarball channel with a postinstall download depends on scripts running and on a second host. Installing from a git URL cannot reach a package that lives in a subdirectory of this repository, so it would have needed a tarball anyway. Compiling on the user's machine would require a Go toolchain for a tool whose point is to be one executable. Requiring `xml2l` on `PATH` moves the setup problem back to the user.

The flag contract belongs to the plugin. oclif rejects unknown flags regardless of strict mode and offers no catch-all command, so a pass-through plugin cannot exist; every flag the plugin accepts is declared, with the same name and shorthand as the binary. That also keeps the layers from drifting silently: an unknown or contradictory flag fails before a file is touched. A JSON-RPC bridge mode was rejected because it adds a second argument parser and a second contract for no user-visible gain.

Machine output belongs to the binary. Each command produces a document describing what it did, and the plugin maps that document into sf's envelope, lifting warnings and preserving exit codes, including `68` for a save that wrote some profiles and failed others. Scraping the binary's prose in the plugin was rejected because it forces every downstream consumer to parse text.

One tag locks the plugin, the six platform packages and the binary. The release workflow refuses to publish unless their versions agree, and the plugin refuses to run a binary that reports a different version. The trade-off is release ceremony — seven packages per release — accepted as the cost of an install that needs no compiler and no network beyond npm. The plugin adds no new profile behaviour: normalization, ordering and conversion remain the binary's, as recorded in ADR-0001 to ADR-0005.
